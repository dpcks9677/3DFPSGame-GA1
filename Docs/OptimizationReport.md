- 프로젝트: Unity 6 (6000.3.22f1) / URP / GameScene
- 측정 환경: Unity 에디터 Play 모드, 1920×1080, RTX 4060 Laptop GPU, VSync 꺼짐
- 측정 도구: 임시 측정 스크립트 PerfProbe (구역당 12초 샘플링, ProfilerRecorder로 수집). 보고서 작성 후 저장소에서 삭제했다.

## 2. 최적화

### 2.1 AI 분석: 병목 진단
베이스라인 측정에서 **GPU 프레임 시간은 약 1.8ms인데 메인 스레드는 약 11~12ms**였다. 이 프로젝트는 GPU가 아니라 CPU(Draw Call 제출과 스크립트)가 병목이다. 그래서 GPU 항목은 "CPU가 제출하는 Draw Call과 SetPass를 줄인다"는 관점으로 평가했다.

### 2.2 제안과 적용 내용
| # | 제안 | 적용 | 결과 |
|---|---|---|---|
| 1 | 미니맵 카메라 경량화 | Far Clip 1000→40, 그림자·HDR·MSAA 끔, Depth/Color 텍스처 복사 끔, 깊이 버퍼 D32+Stencil→D16 | 효과 있음 (FPS +4~12%) |
| 2 | 그림자 비용 축소 | 캐스케이드 4→2, 얇은 바닥·도로 타일 54개의 그림자 캐스팅 끔 후 재베이크 | Draw Call 감소, FPS는 변화 없음 |
| 3 | 오클루전 컬링 | 베이크(데이터 421KB), 메인 카메라 Far Clip 1000→200, Opaque Texture 끔 (쓰는 셰이더 없음 확인) | 효과 있음 (1번 구역 Draw Call 323→187) |
| 4 | 혈흔 이펙트 누수 | `Zombie.cs`에서 생성한 BloodSpray를 1초 뒤 `Destroy` (3줄) | **효과가 가장 큼** |
| 5 | 텍스처 임포트 정리 | 소품 텍스처 9장(수류탄 4, 배럴 3, 지팡이 2) 2048→1024 | 해당 텍스처 75MB→19MB |

적용하지 않은 항목: 모델 Read/Write 끄기(메시 메모리가 전체 17MB뿐이고 파티클 메시 쉐이프 위험), Debug.Log 정리(상태 전이 때만 호출되어 비용 없음), 오디오(전체 2.1MB), LOD·GPU Instancing(SRP Batcher가 이미 켜져 있고 맵이 작음).

### 2.3 원인 분석: 혈흔 누수
`BloodSprayFX` 프리팹이 Loop 켜짐에 Stop Action 없음이라, 좀비가 맞을 때마다 자식으로 생긴 파티클이 영구히 남았다. 좀비를 200번 맞히는 스트레스 시나리오에서 파티클 시스템 600개가 살아 있었고, 수정 후 0개가 되었다.

| 항목 | Before | After | 변화 |
|---|---|---|---|
| SetPass calls | 100 | 76 | -24% |
| Tris | 140.5k | 87.1k | -38% |
| Verts | 244.5k | 149.2k | -39% |
| Shadow casters | 453 | 221 | -51% |
| FPS | 248.0 (4.0ms) | 97.7 (10.2ms) | **악화** |

## 4. 분석

**효과가 있었던 것**
- 혈흔 누수 수정이 가장 컸다. 좀비 피격 시나리오에서 FPS 57→92(4단계 대비), Draw Calls 902→450, SetPass 264→93. 이 문제는 플레이 시간이 길어질수록 누적되는 실제 버그다.
- 오클루전 컬링은 건물이 빽빽한 구역에서 Draw Call을 크게 줄였다 (1번 구역 323→187).
- 미니맵 카메라는 매 프레임 씬을 한 번 더 그리기 때문에, 그림자·HDR·MSAA·텍스처 복사를 끄고 Far Clip을 줄이는 것만으로 모든 구역에서 FPS가 올랐다.
- 소품 텍스처 해상도를 낮춰 텍스처 메모리를 67MB 줄였다.

**효과가 불분명했던 것**
- 그림자 캐스케이드 4→2와 바닥 그림자 끄기는 Draw Call을 줄였지만(1번 419→323) FPS는 변화가 없었다. 프레임 시간을 지배하는 다른 CPU 작업이 있다는 뜻이다. 프로파일러 없이는 그 원인을 확정하지 못했다.
- 2~4번 구역은 90~100 FPS 근처에서 평평하다. 같은 설정을 반복해도 ±5 정도 흔들려서, 4번 구역의 93.5→90.5 하락도 노이즈 범위로 판단한다 (Draw Call은 292→190으로 줄었다).
- 매 프레임 약 50KB의 GC 할당이 있다. 스크립트에서는 원인을 찾지 못했고, 에디터·UI·애니메이터 쪽일 가능성이 있다. 이번에는 해결하지 못했다.

**풀리지 않은 문제: 수동 캡처와 자동 측정의 FPS 불일치**
- 수동 캡처(3.6)의 Before는 248 FPS(메인 4.0ms)로, 자동 측정의 6개 단계 어디에서도 나오지 않은 값이다(자동 측정은 항상 메인 약 10~12ms, 80~100 FPS). 반면 After(97.7 FPS, 메인 10.2ms)는 자동 측정과 같은 수준이다. 즉 Before 캡처만 환경이 달랐을 가능성이 크다. 같은 환경에서 찍은 자료가 아니므로 이 캡처의 FPS로 "최적화가 성능을 떨어뜨렸다"고 결론 내리지는 않는다.
- 다만 오클루전 컬링은 에디터에서 메인 스레드 비용이 늘 수 있다는 가능성은 배제하지 못했다. 자동 측정에서는 오클루전 적용 단계에서 메인 스레드 시간이 변하지 않았다(2번 구역 11.0→10.9ms).
- 확정하려면 Before/After를 같은 세션 조건(같은 창 포커스, 같은 Profiler 상태)에서 다시 캡처하거나, Development Build에서 측정해야 한다.
- 신뢰할 수 있는 결론: **Draw Call, Batches, SetPass, Tris, 그림자 캐스터 수의 감소와 메모리 감소**. FPS 개선은 자동 측정에서는 확인됐지만, 수동 캡처로는 재현되지 않았다.

**한계**
- 에디터 Play 모드 측정이라 에디터 오버헤드가 포함된다. 절대 수치보다 전후 차이로 해석해야 한다. Development Build로는 측정하지 않았다.
- 측정 중 한 번, 에디터가 포커스를 잃으면 Play가 멈춰서 측정이 틀어지는 문제가 있었다. Run In Background를 켠 뒤 처음부터 다시 측정했다 (이 보고서의 수치는 모두 정상 조건).
- 그림자 캐스케이드를 줄여 먼 그림자 품질이 떨어지지 않았는지는 시각적으로 확인하지 않았다.
- 오클루전 컬링은 Static 오브젝트에만 적용된다.

**다음 후보**
- `Zombie.Trace()`가 매 프레임 `SetDestination`을 호출한다. 좀비가 많은 상황(최대 10마리)에서 비용이 클 수 있어 호출 주기를 줄이면 좋다. 이번 측정은 좀비 스폰을 꺼서 포함되지 않았다.
- 프로파일러로 GC 할당 원인과 메인 스레드 지배 작업 확인.
